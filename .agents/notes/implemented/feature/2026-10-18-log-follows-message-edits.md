# Agent Note: 编辑消息同步改写日志行

Status: implemented

## 问题

日志现在只在 `MessageCreate` 时**追加**一行（`<名字>(<uid>) <时间>\n<正文>\n\n`）。玩家发出去之后改了消息——错字、补充描述、改掉说错的台词、补一句关键线索——**日志里留的还是原文**。跑团日志是要拿去复盘和存档的，这种不一致会让 KP 按日志还原剧情时读到玩家早就改掉的版本；校对的时候还得回头翻 Discord 原始消息。

Discord 会为编辑派发 `MessageUpdate` 事件，但这里有几个必须处理的细节：

- **同一事件也会因为链接预览、embed 展开、附件变化而触发**，此时正文没变——不能当成"编辑"再写一行，否则日志会重复；
- 日志行里**没有消息 id**（行格式是 Dice! 兼容的逐字节约定，不能塞 id）；
- 编辑发生在日志 `off`（暂停）或已 `end`（导出）之后时，要不要改？
- 编辑可能来自 partial 消息（缓存里没有完整对象），需要 `fetch()` 才能拿到正文。

## 决策

**记住"消息 id → 行号"的映射**，编辑时**原地替换该行正文**，不动时间戳、名字、uid 和行序。

1. `logs.json` 增加一个键 `msgIndex: Record<logId, Record<messageId, lineIndex>>`（与 `lines` 同一条记录，随同一次 `markDirty('logs')` 落盘，保持原子）。
2. 新增可选能力接口 `LogLineIndexStore`（`src/store/extras.ts`，与 `NickStore` 同一套"冻结契约之外的可选能力"做法）：
   - `appendLogLineForMessage(channelId, messageId, line)`：与 `appendLogLine` 同样的目标选择（`on` 日志 + 场景匹配），追加后记下每个目标日志里的行号；
   - `replaceLogLineForMessage(channelId, messageId, text)`：按索引找到行，**只替换正文**（保留 `name(uid) 时间` 头），返回实际更新的行数。
3. `adapter.ts` 新增 `createLogEditor(store)` 并在 `main.ts` 接 `Events.MessageUpdate`：
   - 跳过 bot、跳过 partial 时正文取不到的情况（`fetch()` 失败就安静放弃）；
   - **正文没变就直接返回**（这是链接预览去重的关键，用 `oldMessage.content === newMessage.content` 判断）；
   - 用与 recorder 完全相同的取名字/附件规则重建正文，再调用 `replaceLogLineForMessage`。
4. **作用范围**：只改 `on` / `off` 状态的日志里的行；**已 `ended` 的日志不动**——它已经导出并作为存档发出去过，事后改写会让"再导出一次"与当初发出去的文件不一致。
5. 正文被清空（例如纯附件消息删掉附件）时**跳过**，保留原行，避免写出空正文的畸形行。

## 测试

1. 记录消息 A 后编辑 A：日志里**仍是 1 行**，正文变为新文本，`名字(uid) 时间` 与行位置不变；
2. `MessageUpdate` 因链接预览/embed 触发且正文未变：日志**不新增行、不改动**；
3. 同一条消息连续编辑两次：仍只有 1 行，且是最新文本；
4. 编辑发生在日志 `off` 期间：该行照常更新（续记后导出的就是新文本）；编辑发生在已 `ended` 的日志：不更新；
5. 编辑 bot 自己的消息、或编辑一条没被记录过的消息：无任何变化；
6. 多条日志同时命中（同一场景理论上只有一条 `on`，但 `sceneIds` 允许一条日志挂多个场景）时，每个命中的日志都更新；
7. 索引落盘：重启后仍能按消息 id 定位到该行（`msgIndex` 与 `lines` 同行号）；
8. 行格式与 Dice! 逐字符断言仍全绿；`npm run check` 通过。

## 曾考虑的替代方案

**把消息 id 写进日志行**（例如行尾加 `#id`）。行格式是与 Dice! 逐字符对齐的约定，测试也按字节断言；加 id 会污染导出文件、破坏兼容，且日志本来就是给人看的。

**不记索引，靠"重扫全日志找同名字+同时间+同正文的行"来定位**。同一秒内同一个人的两条消息就会歧义；而且每次编辑都要 O(行数) 比对，长团日志上万行。

**编辑时删除旧行再追加新行**（保持"最近编辑在最后"）。行序会乱——日志是按时间读的，玩家改一句台词不该让它跑到文末；而且删除会让行号索引整体失效。

**编辑时重新渲染整行（含新时间戳）**。会让日志显示"他说这句话的时间"变成"他编辑的时间"，复盘时间线失真。

**只处理 `on` 状态的日志**。`off` 只是暂停记录，那条日志仍然会被 `/log on` 续记并最终导出；此时不跟编辑，续记后日志里还是旧文本——同一个问题只是延后暴露。

**用 Discord 的审计日志 / 消息历史回填**。需要额外权限、只能回溯有限时间，且与"实时跟随"这个需求无关。

**把 `msgIndex` 独立成文件**（`logindex.json`）。与 `lines` 分两次写盘，崩溃时会留下"行已追加、索引没有"的半截状态；放进同一条 `logs.json` 记录里则是一次原子写入。

## 后果
- **收益**：玩家改错字、补描述、改台词后，日志与 Discord 保持一致；复盘/存档读到的就是最终版本，不用回头核对原始消息。/log export 与 /log end 导出的文件自动是新文本（导出即时从记录生成）。
- **代价（索引漂移风险）**：msgIndex 存的是行号，一旦有人手工编辑 logs.json 的 lines，索引就会指错行。替换前会校验"该行头是否仍是 名字(uid) 时间 形态"，形态不符就跳过而不是盲写——但真正稳妥的前提是别手改数据文件。
- **代价（体积）**：索引约等于日志行数（每条消息一个整数），长团 7000 行的日志多存几十 KB，可接受。
- **已知窗口**：Discord 对编辑事件的派发有轻微延迟，极端情况下（编辑后立刻导出）可能导出到旧文本；这是事件机制的固有窗口，不做额外轮询。
- **对"暂停期冻结"的影响**：off 期间新消息仍然不入日志，但**已记录消息的编辑会跟随**——冻结针对的是"新消息"，内容一致性优先。
- **已 nded 的日志不跟随**：它是已导出的存档，事后改写会让再导出的文件与当初发出去的不一致；需要修正已结束日志只能重新开一条。
